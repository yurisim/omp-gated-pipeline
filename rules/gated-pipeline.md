---
description: Gated plan pipeline (omp-gated-pipeline) - fan-out, deterministic plan preflight, post-implementation adversarial review
alwaysApply: true
agents: main
---

Parallel - fan out by default:
- Before executing an approved plan, or any change touching 2+ files, modules, or features, read skill://parallel-fanout and follow it.
- Plans written in plan mode (local://*-plan.md) MUST include a `## Parallel waves` section in the skill://parallel-fanout format: wave 0 gives shared contracts and every acceptance test verbatim (the architect writes tests first; implementation slices never add tests outside their `owns`); each later wave is a fenced JSON array of slice specs (`id`, `agent`, `owns`, `reads`, `symbols`, `invariants`, `tests`, `acceptance`). Tag every path and symbol the plan creates with `[NEW]`, and list every caller of a changed signature in some slice. Write "Serial: <reason>" in that section when no disjoint slices exist. A serial plan that is one slice with no spec tests and no code, script, test, or build-config edits writes only two lines there, `Serial: <reason>` and `Acceptance: <exact command>`, with no slice JSON; its Approach names every path it touches. Other serial plans still give slice specs and run through the same gates. Executing a plan without the section: add it first.
- When executing an approved plan, run each wave as one `task` batch of its specs' agents (`synth` on Sol for every slice that edits code, scripts, tests, or build config, given contracts rather than implementation code; `sonic` only for verbatim non-code edits), gate every slice and the integration with the project's barrier command (or the no-barrier path in skill://parallel-fanout), and on failure follow the one-retry critic loop in skill://parallel-fanout; "step-by-step" applies between waves, not within one. A JSON-free serial plan runs inline in the coordinator with no `task` batch: gate it with its `Acceptance:` command, then the integration gate unless the plan is docs-only (every file it touches is documentation that no code, test or build reads); on a failed gate the coordinator fixes it and reruns that gate once with the `-retry` suffix, and a second failure stops the pipeline and is reported. No critic runs for it.
- The project's AGENTS.md pipeline section (`Pipeline - <project> specifics`) names the barrier command or the integration command, the test-id format, wave-0 red rules, slice-forbidden commands, baseline-worktree setup, KNOWN sources, and review conventions. A project without that section follows the no-barrier path with its documented full check command as the integration gate.
- Exempt: questions, single-file fixes of about 30 changed lines or fewer, and debugging loops where each step depends on the previous result. New files and larger edits go to `synth` (or a `task` agent on Sol) even outside a plan.

Plan gate - deterministic grounding, no same-weights plan review:
- In plan mode, after writing local://<slug>-plan.md and before proposing it (`xd://propose`), run skill://plan-preflight on it. It costs zero model tokens.
- `pass`: propose immediately. Do not run an adversarial-review pass or a self-critique pass on the plan; synth's Turn 1 Protocol (Sol, a different model family) is the plan's cross-check.
- `fail`: fix exactly the reported diagnostics in the plan (correct or `[NEW]`-tag paths and symbols, add unlisted callers to a slice's `owns` or `reads`), then rerun. After 3 failing runs, `ask` the user with the remaining diagnostics.
- Run it again before spawning wave 1 of an approved plan.
- Review a plan with `adversarial-reviewer-sol` only when the user explicitly asks for a plan review.

Review - adversarial by default (implementation):
- Before the first edit, record `BASE=$(git stash create)` (empty output, or when committing/splitting already-uncommitted work: use `BASE=$(git rev-parse HEAD)`) so the review covers only this change. In a repo with no commits, use `BASE: none (no commits)` and review files whole. Any check failure claimed as pre-existing must reproduce on `$BASE` in `local://<topic>-baseline-checks.md`, never on the modified working tree.
- Before reporting done on any change that edits code, scripts, tests, or build config, read skill://adversarial-review and, after the repo's test suite and checks have run, run one review pass on the `git diff $BASE` patch file (or `git log --stat -p $BASE..HEAD` for a commit series): `adversarial-reviewer` (Opus) on files only Sol agents wrote, `adversarial-reviewer-sol` (Sol) on files the coordinator or any other Opus agent wrote or edited, including wave-0 spec tests; when both apply, spawn both in one batch. Give each the BASE sha, INTENT (the user's request verbatim), SCOPE (artifacts, review concerns, exclusions), raw CHECKS (including `git status --short` and any `planDeviations`), and evidence-backed KNOWN list; handle the verdict as the skill says (1+ CRITICAL or 1+ patch-caused check failure is BLOCK; Accept or Refute each finding, contested findings go to `ask`).
- Review cooldown: one review pass (one batch of one or both reviewer agents) per user request. Fixes made in response to the reviewers' or the advisors' findings are not re-reviewed; re-run the checks they touch instead (a BLOCK clears when its failing check passes or its CRITICAL is fixed). The next review is due with the next review-eligible user request (a code change, per the bullets around this one).
- After a fan-out, review once on the integrated diff, not per slice.
- Exempt: questions and investigations with no edits, docs-only edits, and typo/format-only changes.
